## 审计范围

本轮聚焦「长时间高负载使用」目标下的状态增长面：可视化编辑器 undo/redo
快照栈、历史记录两个 store 的上界与导入合并路径、zenuml 切换 reload
hack 的数据丢失窗口。

## 缺陷与修复

**历史导入合并无上限（产品缺陷，修复 + 判别性单测钉死）**：
`restoreEntries` 对上传文件有 5MB/200 条的输入侧限制，但合并写入时
`[...latest, ...fresh]` **不施加 store 自身的上限**——反复导入可使
manual/auto store 无限增长，最终耗尽 localStorage 配额，打断 codeStore
持久化（正是输入侧限制注释里声明的威胁模型：配额耗尽 → 编辑器自身
静默失持久化）。修复：合并排序后按各槽位上限（auto 30 / manual 200）
截断，最旧先丢；`restored` 计数只计实际留存的条目。

回归测试（historyState.test.ts「caps the merged store」）：150 条导入
→ 再导 100 条新条目 → store 恰为 200 且最旧的 a0..a49 被丢、restored
=100 → 再导 50 条中间时段条目 → 仍 200、挤掉 a50..a99。判别性验证：
暂存修复跑该用例失败、恢复修复通过。

## 审计通过项

- **undo/redo 快照栈有界**：`UNDO_LIMIT=50`，pushUndo 滑窗截断且清空
  redo；redo 长度受 undo 对称约束（≤50）；外部重载（loadFromCode 等）
  双栈清空。快照为 VGraph 深拷贝，上界 = 50×当前图规模，随图生命周期
  释放
- **历史双 store 上界完备**（除上述导入路径外）：auto 30 / manual 200，
  addEntry 写前重读合并（多标签丢失更新防护），dedupe 键只取
  code+mermaid
- **zenuml reload hack 无数据丢失窗口**：`setTimeout(reload, 500)` 触发
  前，代码改动经状态网关同步写 localStorage（persist 无防抖），时间线
  自动保存亦为同步写——reload 时磁盘状态即最新状态
